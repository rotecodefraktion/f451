Deployment

Standardprozess für das Ausrollen neuer Plattform-Versionen in die Produktionsumgebung — verbindlich für das Betriebsteam.

Überblick

Deployments erfolgen ausschließlich über die CI-Pipeline und werden aus dem Branch main ausgelöst. Jede Freigabe durchläuft die drei Zustände working, review und released, bevor eine Version produktiv geht. Ein Deployment gilt erst als abgeschlossen, wenn der automatische Health-Check über alle Instanzen erfolgreich war.

Verantwortlich für den produktiven Rollout ist das Team Betrieb. Änderungen an der Pipeline selbst prüft zusätzlich das Team Entwicklung.

Umgebungen

Die Plattform läuft in drei Umgebungen. Staging spiegelt die Produktion vollständig, dient aber nur der Vorabprüfung.

Zugänge

Der Zugriff auf die Produktionsumgebung erfolgt über den zentralen SSO-Login. Deployment-Rechte werden ausschließlich über die Gruppe ops-deploy vergeben und quartalsweise überprüft.

Ablauf

Ein Deployment wird in drei Schritten durchgeführt. Prüfe vor jedem Rollout den aktuellen Stand des Ziel-Branches:

Terminal · bash
# 1 · Aktuellen Stand prüfen
git fetch origin main
git status

# 2 · Pipeline auslösen
f451 deploy --env production --tag v2.4.0

# 3 · Health-Check beobachten
f451 status --watch
HinweisFühre produktive Deployments nie während der Kernarbeitszeit (09–17 Uhr) durch. Nutze die Wartungsfenster am Dienstag- und Donnerstagabend ab 20 Uhr.

Rollback

Schlägt der Health-Check fehl, wird die Version automatisch auf den vorherigen Stand zurückgerollt. Ein manueller Rollback ist jederzeit über f451 rollback --env production möglich; der fehlerhafte Stand bleibt für die Analyse erhalten.
